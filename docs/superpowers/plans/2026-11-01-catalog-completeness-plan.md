# 点歌目录完整性与限流优化计划

## 范围和当前状态

目标：个人歌单、歌手歌曲在网易云接口和账号权限允许的范围内逐页完整浏览；支持大型列表，同时保持点歌、切歌、本地曲库、多屏及互动。20 台是设计上限，未做实机容量或压力测试。

工作区含此前未提交的二维码、Docker、互动和其他修改，不能直接覆盖或全部打包。本轮还有中断的歌手改动：`src/api/artist.js`、`src/electron/ipcRenderer.js`、`src/remote/main.js` 和未跟踪测试。它尚未验收、提交或部署，不应作为完成结果；实施前逐项审查并整合，不能把实验代码直接发布。

## 代码证据

1. 个人歌单歌曲：`src/electron/ipcRenderer.js` 的 `hostCatalog('playlistTracks')` 调用 `resolvePlaylistCatalogTracks(id, 100)`。后者从 `trackIds` 最多取前 100 个 ID，返回前也截取到这个上限。因此歌单超过 100 首必定无法通过该路径完整显示。`src/remote/main.js` 的 `renderPlaylistTracks` 对已收到的数组本身没有同样的 100 首截断。
2. 个人歌单列表：`getUserPlaylistAllowlist` 优先直接使用 store 预加载内容，否则单次调用 `userPlaylist`，limit 2000、没有 offset；`src/store/actions.js` 的预加载也有同样单次 limit。若预加载不完整，KTV 可能直接复用它；具体缺少多少需结合用户账号与实际响应验证。
3. 歌手歌曲：Git HEAD 的 `hostCatalog('artistTracks')` 使用 `/artists` 的热门歌曲并截取 30 首；点歌页 `renderArtistTracks` 原先又截取 30 首。未完成实验改动将上游改成 `/artist/songs`，但仍限制 300 首或 512 KiB，且一次取多页后整体返回，所以仍可能不完整或超时。点歌页现有实验改动只移除了渲染端 30 首截断，不能单独解决上游限制。
4. 主屏桥接：`KaraokeWebHost` 的 host 请求体上限 1 MiB、命令期限 12 秒；直接一次返回大歌单会碰到大小或超时边界。客户端已有 generation，可作为切换歌单时丢弃旧页的基础。
5. 现有限流以客户端、房间和接口类别区分。搜索每设备 10 秒 10 次，房间 80 次；设计目的是防止输入、误触或并发请求占满主屏桥接与上游。分页也受对应接口的客户端和房间限流约束，不能高速循环大量页。
6. 上游歌单的 `trackIds` 可能完整而 `tracks` 不完整；权限、下架及账号状态也可能造成上游无法返回全部详情，不能把返回空缺都判断成本项目截断。

## 方案与代码位置

### P0 基线和已有修改审查

- 记录 HEAD、线上 manifest、工作区差异，独立保留未提交改动；比较线上与工作区实际代码。
- 使用可控模拟数据分别构造 0、30、100、101、300、301、1000 条及上游缺项、超时场景，记录顺序、返回数、响应体字节、每页耗时；真实账号只做用户允许的正常读取，不记录 token、歌单名称或歌曲列表。
- 审查中断的 300 首实验及测试，确定保留哪些实现；不得清理用户文件或混入未经审查的既有修改。

### P1 分页协议和个人歌单

- 在 `src/electron/ipcRenderer.js`、`src/electron/karaoke/KaraokeRemoteApi.js` 和 Router 增加向后兼容的 `offset`/`limit`，建议每页默认 100、服务端最大 100；页响应包含 `tracks`、`offset`、`hasMore`，有可靠总数时附 `total`。旧请求保持现有响应形状和授权语义，禁止客户端绕过歌单 allowlist。
- 对歌单 `trackIds` 按页切片，再按最多 100 ID 分批获取详情并恢复原顺序；上游缺失项不伪装成已完整加载，显示已返回与不可用数量。对歌单列表也处理 offset/more；不能盲信已有预加载已完整。
- `src/remote/main.js` 先显示首屏，在用户滚动/点击“加载更多”时按序拉下一页；不让 1000 首产生大包和全量 innerHTML。切换歌单或账号时取消/丢弃旧页，分页失败保留已显示内容并允许重试；本地列表不受影响。

### P2 歌手目录

- 使用现有本地 API 的 `/artist/songs`，按歌曲分页传递，不依赖 `/artists` 热门歌曲接口充当完整目录。沿用 `artistTracks` 权限检查、缓存代际隔离和曲目清洗。
- 页响应和 UI 同 P1；为热门排序保持顺序、按 ID 去重。将已有 300 条/512 KiB 静默截断实验替换为有界分页；不改主应用其他调用 `getArtist` 的既有行为。
- 核对上游 API 返回 `more`、`total`、异常码以及登录权限的真实行为；接口不提供某曲时明确提示，不承诺绕过版权或账号限制。

### P3 限流和资源使用

- 先用客户端串行分页、页缓存/单飞和用户触发的继续加载控制请求；列表请求与搜索、availability、互动独立计数，不能让某个大列表占满其他功能。
- 429 返回或保留可计算的 `Retry-After`，显示等待并按需恢复当前页；取消/隐藏/切换时清理等待任务，自动重试次数有界。根据本机测量和最多 20 台目标调整额度，保留房间级保护，不直接取消全部限流。
- 缓存按账号、资源、页码、排序和 generation 区分；明确 TTL/容量与退出、换账号、强刷的失效方式。结果追加时保持焦点、滚动位置和已选歌曲。

### P4 测试、部署和回滚

- 单元和集成：个人歌单与歌手超 100/300 首、多页顺序及去重、缺失歌曲、后页失败、重试、账号切换、旧响应、缓存隔离、429 自动恢复、桥接包体限制；有可控时钟和模拟上游，不对生产网易云做密集请求。
- 回归现有 Guest 切歌、Remote 首曲自动开唱、本地增量索引、推荐歌单、多屏与互动；每阶段运行定向测试、检查 diff，再进入下一阶段。
- 构建后使用 ego-browser 在本机测试首屏、加载后页、切换歌单和搜索/点歌；真实手机、账号权限及 20 台设备未实测时明确标注。
- 完整审查全部需要发布的未提交代码，生产构建、Source CI 和版本指纹通过后备份软路由当前 dist/镜像，原位更新挂载目录并仅重启必要容器；重启会结束房间。核对健康、版本和线上正常低频浏览；保留可回滚备份。

## 已知限制

- 根因来自当前源码；本轮未拿用户实际歌单与线上返回条目逐一核对，无法断言所有缺失都由上述截断造成。
- 此文为计划，不代表修复、测试、提交或部署完成。用户只要求继续调查和制定计划，后续实施需按计划逐项验证。
