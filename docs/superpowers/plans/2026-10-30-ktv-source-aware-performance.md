# KTV 点歌及多屏分来源性能优化实施计划

> **执行提示：** 按阶段实施；每阶段先记录基线和可复现证据，完成对应测试与 diff 审查后再继续。以实际测试决定具体参数，不预设已达到的性能。

**目标：** 在总设备不超过 20 台（包括主屏、副屏及点歌设备）的局域网场景下，降低状态同步延迟，避免本地数据和网易云请求互相拖累，保持既有功能。

**架构：** 保留现有房间、主机桥接和点歌协议，按房间实时状态、本地曲库、网易云目录、互动事件分别治理。优先修复已确认的重复工作；实时推送仅在现有轮询实测不能满足需求时另立阶段评估，不提前引入重构。

**技术：** Vue 2、点歌页原生 JavaScript、Node.js、Docker、现有测试脚本和 ego-browser。

**需求来源：** 用户要求按实际数据来源区别处理所有点歌模块，并以 20 台设备为容量目标。

## 全局约束

- 保留 Guest 切歌、Remote 第一首自动开唱、本地曲库及增量索引、主副屏同步、互动应援。
- 现有未提交工作与本机数据均保留；不将用户歌曲、凭据、临时产物纳入提交。
- 状态刷新、目录请求、互动请求分别计量；不得以删除功能、关闭更新或伪造成功提示换取速度。
- Docker 与本机服务分别记录版本；真实手机、真实软路由结果只能在实际验证后报告。

## 当前代码事实

| 模块 | 当前路径及来源 | 目前策略和待核验点 |
| --- | --- | --- |
| 正在演唱、等待队列、已播放 | `src/remote/main.js` → `/state` → `KaraokeRemoteApi.js` 房间快照 | 前台 500 ms、隐藏 5 s；按 revision 更新队列与历史；点歌成功后立即合并刷新。 |
| 主屏到服务端 | `src/karaoke/webRoomBridge.js` → `/ktv/host/exchange` | 空闲 200 ms，任务进行中 80 ms；单飞；大歌词、外观和分析数据按版本发送。检查请求体及桥接负载。 |
| 副屏 | `src/karaoke/displayPoller.js` → `/ktv/display` | 前台 500 ms；隐藏暂停；歌词、外观、节拍时间线按版本单独读取。检查多副屏 CPU、延迟、重复渲染。 |
| 本地歌单 | `/local-playlists` → 主机桥接 → 本地索引 | 当前并发读取已合并，不保留长时列表缓存；失败允许重试。检查首次扫描与增量索引，不把读取当成重新扫描。 |
| 在线搜索、推荐、歌手、账号歌单 | `/search`、`/recommendations`、`/artists/*`、`/playlists/*` → 主机桥接及网易云数据 | 搜索有 350 ms 输入防抖和并发合并；多个目录有 TTL 缓存。需确认失败、登录变更、强制刷新时的缓存边界。 |
| 互动应援 | `/reactions` → 房间服务及事件队列 | 用户触发时发送；主副屏通过各自状态同步获取；需测发送至显示延迟及并发公平性。 |

进入点歌页的 `prefetchCatalogModules` 当前同时启动推荐、默认歌手、本地歌单和用户歌单；默认歌手查询会产生六个歌手搜索请求。多人同时进入可能使房间级歌手搜索限额或主机桥接繁忙，这是待实测风险，不代表已测得故障。桥接队列上限为 64 项、命令超时为 12 秒；点歌会话上限为 32，实际目标仍是包括主副屏在内的 20 台设备。

## 阶段一：基线与问题定位

- [ ] 保留当前本机配置及源码改动，确认测试环境和软路由部署版本；不影响用户正在使用的房间。
- [ ] 以匿名统计记录每类请求数量、耗时、错误码、缓存命中及桥接队列深度；不记录 token、搜索内容或歌曲隐私数据。
- [ ] 分别测 1、5、10、20 台设备的模拟组合（至少含 1 主屏、1 副屏及多个点歌端），覆盖同时进入、连续搜索、多人点歌、切歌、显示同步、短暂断网恢复。
- [ ] 分别记录：主屏操作至副屏／点歌页可见时间、搜索及本地列表首次／再次打开耗时、交互应援延迟、失败率、请求数和 CPU／内存。报告中标明模拟和真实设备的区别。
- [ ] 使用 `node scripts/test-karaoke-state-capacity.js`、`node scripts/test-karaoke-web-host.js`、`node scripts/test-karaoke-web-bridge.js`、`node scripts/test-karaoke-display-client.js` 验证基线并保存结果。

## 阶段二：房间状态和多屏实时路径

- [ ] 检查 `src/remote/refreshScheduler.js`、`src/remote/main.js`、`src/karaoke/displayPoller.js` 和 `src/karaoke/webRoomBridge.js`，确保每个资源只存在一个轮询 owner；突发操作后的刷新与周期刷新合并，避免并发重复请求。
- [ ] 保持当前 200 ms 主屏、500 ms 前台显示／点歌的初始设置，依据阶段一的真实开销调整；网络失败使用有上限的退避，前台恢复时立即刷新。不得把计时器设定当成端到端延迟。
- [ ] 排查 `renderNowPlaying`、`renderQueue`、`renderHistory` 及副屏 Vue 更新：未变化的数据不反复重建；曲目、封面、状态或 revision 更新必须可见；歌词和资源缓存不得跨歌曲误用。
- [ ] 如果实测轮询仍无法同时满足延迟和负载，单独评估 SSE/长轮询：需有断线恢复、版本补偿、连接清理、隐藏页策略及旧客户端兼容。此项实施前先比较复杂度和实测收益。
- [ ] 运行 display-client、display-lifecycle、web-bridge、web-host、remote-api 与状态容量测试；比较基线并审查 diff。

## 阶段三：本地曲库

- [ ] 检查 `KaraokeRemoteApi.js`、`KaraokeWebHost.js` 及本地曲库模块：读取列表使用现有索引；显式刷新及增量索引仍可看到新增、变更和删除。
- [ ] 保留正在进行请求的合并，验证 19 点歌端并发只执行一次同资源读取；失败后可重试，取消一个请求不能中断其他请求，不缓存错误或空结果为永久成功。
- [ ] 测量大曲库的列表体积、metadata/LRC/封面重复读取；只有观察到瓶颈才增加版本缓存或分页，确保搜索、点歌、歌词和封面语义不变。
- [ ] 运行本地曲库、catalog-performance、remote-api、web-host 测试；检查增量索引与本地首曲播放。

## 阶段四：网易云及账号目录

- [ ] 审核 `src/remote/main.js` 的 `prefetchCatalogModules`、默认歌手搜索和 `src/electron/karaoke/KaraokeRemoteApi.js` 的缓存。基于基线决定是否先展示已内置的歌手数据，再合并或延迟预热；切换模块时立即加载，不能删除推荐、搜索或歌手功能。
- [ ] 对在线搜索及目录请求按相同参数做 single-flight；区分失败与空结果，合理限制缓存大小和生命周期；账号或房间变化、手动刷新后避免显示旧账号数据。
- [ ] 将在线请求的超时、取消、错误提示和重试与房间状态隔离；请求慢不能阻塞状态、Guest 切歌、自动首曲或本地歌单。
- [ ] 运行 catalog-performance、remote-api、web-bridge、登录／歌单相关测试；对比 1／20 设备进入时上游和桥接请求数。

- [ ] 每阶段记录修改路径、问题、根因、修改、保留功能、测试结果和可比较的性能数据；审查已有未提交改动，避免混入截图及个人文件。
