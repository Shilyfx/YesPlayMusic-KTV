# LumaSing 下一阶段运行速度优化计划

> 状态：用户已批准的有证据修复已逐项完成、验收、提交并部署软路由。P5 完成 10 分钟连续运行与线上浏览器检查；30–60 分钟长期观察、真实多设备/声音验收仍未完成。条件方案没有证据时不实施。以下版本事实保留计划制定时的历史状态，最新结果以 `2026-10-31-performance-release-result.md` 及各阶段报告为准。

**目标：** 在不超过 20 台设备（含主副屏）的内网使用场景，缩短点歌、队列更新和歌词显示的等待，降低页面卡顿、重复请求及长期运行资源占用。

**方法：** 延续分来源优化，优先处理已有证据的重复工作。先建立同版本测量，再逐项减少重复读取、传输与渲染；推送机制和大规模架构变更作为后续决策项。

**技术范围：** 现有 Vue 2、原生点歌页、Node/Docker、Folia 渲染、现有测试脚本与 ego-browser。此次计划不要求增加框架或升级依赖。

## 3. 按来源设计预算

| 数据类别 | 覆盖模块 | 策略 |
|---|---|---|
| 应用内部实时状态 | 正在演唱、等待队列、已播放、主副屏状态 | 操作后及时刷新；周期同步作补偿；不等待在线目录请求 |
| 内部互动事件 | 手动应援、播放/暂停/切歌/点歌联动 | 立即发送和本地按钮反馈；保持事件顺序、有效期、公平性 |
| 本地曲库数据 | 本地歌单、metadata、LRC、封面 | 使用索引；同次扫描合并；按资源版本读取与缓存 |
| 网易云公共目录 | 搜索、歌手、榜单、公共歌单 | 同参数请求合并；输入防抖；限制预加载并发；有界缓存 |
| 网易云账号数据 | 我的歌单、账号推荐、权限与可用性 | 带账号/会话隔离；登录退出、强制刷新、房间切换失效 |
| 播放媒体 | 在线 URL、音频下载、本地文件、解码与起播 | 将取 URL、首字节、可播放、实际播放分别计时；过期 URL 不盲目复用 |
| 浏览器视觉资源 | Folia、角色、图片、模型 | 按功能加载；复用编译和解析结果；后台暂停；离开释放 |

## 4. 实施顺序与验收

### P0：统一版本与测量口径

**文件：** 版本记录、现有构建/打包脚本、`scripts/measure-karaoke-performance.js`、既有性能文档。

- [ ] 比较主工作区、发布目录和 Docker 指纹，逐项记录待保留、待评审、已部署修改；未经审核的音频改动不可混入性能发布。
- [ ] 建立可复现发布记录：Base SHA、审查后的提交、静态入口/后端校验值、构建命令、回滚位置。
- [ ] 对点歌、切歌、内部状态、在线搜索、本地列表、样式切换分别记录耗时；拆分客户端、后端、主机桥接、上游四段。
- [ ] 采样请求次数/体积、缓存命中/失效、DOM 更新次数、长任务、帧时间、CPU/内存；日志不包含 token、cookie、完整搜索内容。
- [ ] 使用同一设备、曲目、样式、版本配置对比优化前后。首次与缓存命中分开；样本不足不报告 p95。

**完成标准：** 有可复现版本与基线；不能把纯内存脚本耗时报告成网络或实机数据。

### P1：点歌页首开与模块切换（优先）

**文件/函数：** `src/remote/main.js` 的 `prefetchCatalogModules`、`ensureModuleLoaded`、`loadRecommendations`、`loadPlaylists`、`loadLocalPlaylists`、`loadReactionPreviews`；`src/electron/karaoke/KaraokeRemoteApi.js`。

**代码依据：** 进入页面仍会启动推荐、本地列表、用户歌单预加载；全量列表及表情预览存在 innerHTML 构造路径。是否构成瓶颈由 P0 测量确认。

- [ ] 正在演唱、当前模块及用户动作优先；非当前目录安排为低优先级预热，建议最多 1 个后台目录任务，实际值按测量调整。
- [ ] 用户进入某模块时提升该模块的加载优先级，并复用已有请求；后台失败不阻塞状态和切歌。
- [ ] 搜索输入继续显示完整当前查询结果；使用取消或 generation 阻止旧结果覆盖新结果。先检查已有实现，再决定补齐点。
- [ ] 本地/在线列表分别缓存；刷新本地不触发网易云，在线服务失败时本地仍可用。
- [ ] 仅在首次进入互动模块时准备必要预览；页面隐藏或离开后暂停预览实例，展示内容和角色选择全部保留。
- [ ] 长列表仅在测出 DOM 瓶颈后采用分页或虚拟列表；搜索仍覆盖全集，保留焦点、滚动位置、点歌状态。

**验证：** `test-karaoke-catalog-performance.js`、`test-karaoke-remote-api.js`、ego 首开/切 Tab/连续搜索/在线失败场景。比较首屏可操作时间、启动在线调用数、切换模块耗时与 DOM 节点数。

### P2：主副屏与点歌端实时状态

- [ ] 保持每资源一个轮询 owner，检查正在刷新时周期请求和 mutation refresh 的合并语义；不可遗漏刷新期间到达的新变更。
- [ ] 队列/历史、歌词/外观、播放时钟、互动事件各自判断变化；未改变的较大对象不重新解析、复制或触发舞台构建。
- [ ] 将时钟推进与业务状态更新解耦；副屏利用现有本地时钟平滑显示，校时与歌词偏移保持原有含义。
- [ ] 主屏歌词和外观仍按版本发送；只有测得序列化重复耗时才改为事件驱动的版本缓存。

## 5. 拟定目标（待基线确认，均不是已达到结果）

| 指标 | 初步目标与测量边界 |
|---|---|
| 按钮点击到本地操作反馈 | 100ms 内显示处理中/成功/失败，不伪造服务端完成 |
| 主屏操作到副屏/点歌端可见 | 健康局域网、前台、非上游操作，p95 争取 ≤800ms；未满足时先拆解链路 |
| 内部状态 HTTP | 软路由正常负载下 p95 争取 ≤100ms；不包含网易云和音频下载 |
| 已加载模块再打开 | 争取 ≤200ms 完成首个可操作视图；缓存失效时显示更新状态 |
| 在线搜索 | 分开记录输入防抖、内部等待与上游耗时；不承诺网易云固定响应时间 |
| 歌词渲染 | 以原效果质量为前提，记录帧时间分布、>50ms长任务和掉帧；60Hz设备争取接近16.7ms帧预算，不把平均FPS当稳定性结论 |
| 长期运行 | 离开模块后实例数量回落，缓存有上限，重复切换无持续无界增长 |

## 6. 方案取舍与建议

1. **建议采用：分来源、逐路径减少重复工作。** 复用现有机制，容易与当前体验比较，也便于定位回归。
2. **后续条件方案：推送替换部分轮询。** 可能改善同步延迟，但增加重连与状态一致性成本；只有 P2 实测说明必要时才进入设计。
3. **暂不采用：统一加快全部轮询或全面重构。** 不能解决网易云慢和渲染卡顿，且可能增加主屏及软路由开销。

**建议先执行 P0→P1→P2，交付第一批可测收益；随后执行 P3→P4→P5。** 不先承诺提速百分比。现有音频修复应先得到用户真实使用反馈，任何声音回归阻止继续发布。
