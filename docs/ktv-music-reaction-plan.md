# KTV 音乐实时联动与互动优先级方案

日期：2026-10-27。状态：第一阶段（Gate A 安全音频接入、自适应音乐状态机、服务端多人互动优先级调度器、主副屏双层协同）已实现并通过自动化验证，详见 [实现与验证记录](music-reaction-linkage-validation.md)；第二阶段可选低延迟 SSE 通道按需独立推进。

## 1. 先回答时间问题

**运行时采用边播放、边分析，不需要等整首歌曲分析完成。**

- 主电脑本地节奏小动作：目标在检测到变化后约100–200ms响应，这是待实测目标。
- 情绪表情切换：刻意观察约1–3秒，确认变化稳定后再切换，避免每个鼓点都变脸。
- 新歌起播：用约6–10秒建立本首歌的音量基准，期间显示聆听或开唱状态。
- 当前主电脑交换和副屏拉取各约1秒一次。沿用它们时，远端表情变化可能额外延后约1–2秒，网络阻塞时更久，不能承诺副屏毫秒级跟拍。
- 如果要求主副屏更接近同步，第二阶段增加单一SSE推送通道，目标把状态传送延迟降到局域网约100–300ms，实际效果需要测量。

**开发与验证估计：基础稳定版约12–20小时，通常约2–3个工作日。**先用2–4小时做播放兼容性验证，再决定可覆盖的音频来源。若需要新建音频代理、适配输出设备，另增加约1–2个工作日；低延迟SSE推送另估4–8小时。以上是工作量估计，不是已完成结果或固定交付日期。

## 2. 现有代码给出的约束

- `src/utils/Player.js` 的 `_playAudioSource()` 使用Howler的 `html5: true`，不能假设接到 `Howler.masterGain` 就能读到当前歌曲。
- 同一文件的 `setOutputDevice()` 使用媒体元素的 `setSinkId()`。接入Web Audio后需要重新验证输出设备行为，不能为表情改坏原有音频输出。
- `src/karaoke/webRoomBridge.js` 的 `loop()` 在每次交换结束后约1000ms安排下一次交换；`src/karaoke/displayPoller.js` 也约1000ms取一次显示状态。实际延迟包含两段调度、请求和页面处理时间。
- 常驻角色与临时登场已分为独立图层；临时表情有自己的角色、文字、出场方式、实例和淡出过程，可以复用。
- 现有互动事件过期时间8秒、采用最新事件覆盖。若增加多人排队，必须同步调整过期和确认机制，不能仅在前端增加数组。

## 3. 推荐架构：主电脑分析，房间调度，各屏展示

```text
主电脑当前歌曲
  → 单一音频分析器（约20次/秒，本地）
  → 平滑、强弱/节奏特征、状态判断
  → 常驻角色的情绪/动作状态
  → 沿用房间同步；可选SSE推送
  → 副屏按共同的播放时间轴展示

手机互动 → 已有认证接口 → 房间互动调度器 → 临时登场图层
                                ↑
                     自动音乐表情不抢占这个图层
```

Docker软路由负责验证和同步小型状态，不进行音频解码或逐帧分析。手机不重复播放或分析歌曲；副屏不重复创建音频分析器。第一版不采集麦克风，不把音频上传到云端。

## 4. 音频接入必须先通过兼容性 Gate

### Gate A：找到可分析且不破坏播放的路径（估2–4小时）

1. 核对HTML5媒体元素、实际音频URL和跨域响应，分别测试在线歌曲与本地来源。
2. 测试浏览器支持、声音、暂停恢复、拖动进度、切歌、静音、音量和输出设备。
3. 仅为验证通过的路径接入分析。跨域条件不满足时保留原播放器，降级为播放状态微动画，不假装读到了音乐强弱。
4. 不额外下载整首歌用于分析，不同时播放第二份音频，不反复创建媒体源节点。

W3C规范明确：跨域条件不满足时，媒体元素音源节点会输出静音。因此不能在当前HTML5播放路径上盲目插入节点。若必须走同源音频代理，需要另外设计受限来源、鉴权、Range、缓存和带宽上限，作为单独变更验证。

参考：[W3C Web Audio：MediaElementAudioSourceNode 安全约束](https://www.w3.org/TR/webaudio-1.1/#MediaElementAudioSourceOptions-security)。

**通过条件：**支持的路径上声音与原先一致；不能确认安全的来源维持原播放，不开启分析。没有通过此Gate，不进入强弱识别实现。

## 5. 第一版分析哪些特征

| 特征 | 用途 | 控制方式 |
| --- | --- | --- |
| 短时RMS能量 | 判断当前较轻、适中还是强烈 | 相对本首歌近期基准，不靠固定音量阈值 |
| 低频能量和瞬态变化 | 产生轻微点头、弹跳 | 动作频率有上限，不要求第一版准确估计BPM |
| 高频/整体能量上升趋势 | 判断段落正在增强 | 观察1–3秒，避免单次爆音触发 |
| 持续安静、暂停或缓冲 | 回到聆听、休息状态 | 区分播放器状态和音频安静，静音不等于暂停 |
| 实际播放时间与歌曲ID | 对齐动作，排除旧歌曲数据 | 切歌、拖动进度后重置分析窗口 |

建议状态为：聆听、轻快、兴奋、持续高能量、缓和回落。对应专注/开心/惊讶/庆祝等角色状态，三个角色保持相同语义。

- 情绪至少保持约4–6秒；进入和退出阈值不同，形成迟滞，减少来回切换。
- 撒花等大动作冷却约15秒，不连续占满歌词画面。
- “柔和、标准、热闹”只调整动作幅度和触发敏感度，不改变歌曲播放。
- 安静时有呼吸、眨眼和轻微目光动作；播放增强时动作更明显。
- 高能量不能可靠代表副歌、开心或伤心。第一版应称为“音乐强弱联动”，不称为理解歌曲情绪或准确识别高潮。

## 6. 用户互动发生时，自动表情怎样处理

**两层显示，音乐状态持续更新，用户互动占据前景。**音乐分析器不因有人发送表情而重启；只暂时让出展示空间。

| 同时发生的情况 | 推荐处理 |
| --- | --- |
| 音乐自动表情 + 手机互动 | 手机互动优先登场；常驻角色淡出，自动状态只更新到内存，不显示、不积压 |
| 互动结束 | 约400–450ms平滑恢复到“此刻”的音乐状态，不恢复到互动发生前的旧表情 |
| 同一个人连续发送 | 保留当前连续操作语义：旧表情约160ms淡出，新表情从中心重新登场，重新计时；不原地换字 |
| 不同的人同时发送 | 由服务端统一安排，建议最多1个正在展示、2个等待，按公平顺序处理 |
| 等待队列已满 | 返回明确的繁忙提示，不先显示“已发送”再静默丢弃 |
| 手机自定义内容 | 和角色、表情、出场方式作为同一条不可拆分的事件调度，不受后来的自动文案覆盖 |
| 展示期间暂停 | 立即更新底层为休息状态；当前人工应援可以播放完，结束后恢复休息角色 |
| 切歌或拖动到新段落 | 清除旧音乐分析窗口。旧歌曲关联的待播互动取消；正在展示的旧歌曲互动快速淡出，不带入下一首 |
| 正常唱完 | 停止音乐强弱动画，可在人工互动结束后给出一次收麦动作；切歌不算正常唱完 |
| 房间结束、页面隐藏或关闭互动 | 取消动画、计时器和待播事件，停止对应采样/展示，不在恢复后补播旧事件 |

### 调度与确认细节

- 调度权放在房间服务端，不能由每块屏幕独立排队，否则各屏可能显示不同顺序。
- 事件包含：房间代次、事件ID、发送者匿名会话ID、歌曲ID/作用域、角色、表情、自定义文字、出场方式、开始/结束时间和最后可开播时间。
- 待播消息建议最长等约8–10秒。事件传输保留期可以到20秒，但“保留可去重”不等于“20秒后还允许登场”。
- 手机返回“已安排/排队中/繁忙”，成功响应附事件ID与预计开始时间。过期或歌曲已切换必须有对应反馈。
- 维持现有每人及全房间发送限制；同一发送者连续替换不应挤占多个排队席位。一个人不能用连点永久排挤其他已等待的人，建议其他人已排队时同一人的替换最多延长当前席位一次。
- 所有屏幕依据服务端时间校准，晚收到但尚未结束的事件跳到正确进度，不重新从头播放；已结束的事件只记去重游标。
- 发送者会话ID只在服务端调度时使用，发给屏幕的数据去除身份字段；认证令牌始终不进入显示数据。
- 先实现确定性的调度器单元测试，再接界面。具体排队上限和文案可在体验测试后调整。

## 7. 同步、性能与清理

第一阶段复用已有同步请求，只同步情绪状态、强度、播放时间、版本和有效期，不逐次发送FFT数组。状态相同不重复广播；节奏小动作在各屏依据共同时间轴本地生成。此模式不能保证每个真实鼓点跨屏严格同步。

如果需要更快人工互动和更小跨屏误差，第二阶段用SSE传送低频状态变化与服务端调度事件。每页面只有一个连接owner；歌词/播放控制仍走已有机制。需要断线续传游标、房间代次、过期丢弃、带退避重连，以及Nginx关闭该通道的缓冲。SSE只传可公开的显示数据，不传主机令牌、手机令牌或命令。

采样只在主电脑持有当前音频来源时运行。数组复用，节点按实际媒体元素管理，切歌销毁旧引用，退出房间关闭分析器；不每帧写Vuex/localStorage，不为每块副屏加轮询。页面隐藏按产品是否仍需主机后台播放单独降频：保留必要状态更新，避免高频视觉计算。

## 8. 文件与实施顺序

1. 审查 `src/utils/Player.js` 与 `src/karaoke/KaraokePlayerAdapter.js` 的实际音频生命周期，完成Gate A，不先改默认输出链。
2. 新增 `src/karaoke/musicReactionAnalyzer.js`：采样与特征；新增独立的音乐状态控制器，处理平滑、迟滞、冷却和歌曲代次。
3. 新增服务端互动调度器并接入 `src/server/KaraokeWebHost.js`。先测试多人公平、连续替换、过期、切歌取消和会话隔离。
4. 扩展 `src/karaoke/webRoomBridge.js`、`src/karaoke/displayPoller.js` 的显示状态字段，保持single-flight，不扩大轮询频率。
5. 接入 `ReactionOverlay.vue` 的常驻层与临时层；增加优先级控制，验证自定义文字与角色不会被自动状态覆盖。
6. 本地模拟音频测试后再进行真实歌曲、软路由及实体多电脑/手机验收。低延迟SSE作为第二阶段，独立验证和部署。

## 9. 预计工作量与验收 Gate

| 阶段 | 估计 | 必须拿到的证据 |
| --- | --- | --- |
| 音频兼容性验证 | 2–4小时 | 支持来源清单、正常声音、暂停/恢复、音量/输出设备均正常 |
| 分析器与状态控制 | 3–5小时 | 静音/渐强/强拍测试片段，状态平滑、冷却和切歌重置测试 |
| 人工互动调度和图层协调 | 3–5小时 | 同人连点、多人排队、暂停、切歌、自定义内容的确定性测试 |
| 真实播放与Docker验收 | 4–6小时 | 连续歌曲、断线重连、内存/CPU记录、实际主副屏和手机检查 |
| 可选SSE同步增强 | 另4–8小时 | 实测延迟、掉线恢复、重复事件防护、无重复连接owner |

基础版合计12–20小时。跨域音频代理、某些浏览器/输出设备不兼容可能增加工期；必须先说明Gate A结果再承诺覆盖范围。

验收前后都保留Guest切歌、Remote首曲自动开唱、本地曲库与增量索引能力。性能目标及实际结果分开记录，不能用浏览器模拟冒充实体设备测试。
