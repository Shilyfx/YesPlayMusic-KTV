# 统一公网入口与多房间：初步方案

## 现状

现网 `ktv.shilyfx.icu` 通过云端反向代理与隧道连接一台软路由，房间状态及凭证由该软路由进程持有。网页主屏使用 `KaraokeWebHost` 的公网来宾入口；Electron 使用自己的 `KaraokeServer` 局域网房间，不会自动接入软路由的公网房间。故现状不能把这个域名视为支持多台主机、多个独立房间的公共服务。

## 建议架构

保留同一域名，由云端房间网关区分房间：主机安全地注册房间并建立持续的出站连接，网关把带房间标识的请求转发到对应主机；手机扫码通过 `https://域名/room/<房间标识>` 入场。Mac、Windows 和软路由各自保持本机的播放和队列，云端不直接持有设备的管理权限。单纯修改现有反向隧道端口不能实现多房间隔离。

- 每个房间生成单独的随机标识、来宾凭证和主机连接凭证；结束时撤销，房间之间状态、请求、搜索权限、互动和控制互相隔离。
- 网关负责在线状态、连接保活、超时清理、断线重连与按房间转发；区分主机断线与房间主动结束，防止旧连接恢复后控制新房间。
- 保留现有软路由单房间接口与二维码，提供兼容迁移；公网入口和云端主机通过配置而非写死，域名、证书与部署步骤写入更换文档。
- 限制来宾权限与每房间资源消耗，明确错误和重试状态；日志不记录凭证。公网入口默认不暴露本地音乐文件和主机管理接口。
- Mac/Windows 桌面需要新增网关连接及互动接收；云端只中转授权的操作和数据，不将一台主机的 LAN 服务直接暴露到公网。跨平台需要验证桌面音频、待唱队列、歌词、副屏和互动。

## 实施前要明确

房间是否仅在用户创建时产生、是否需要密码或公开房间列表、预期同时在线房间数、音频是否只在各自主机播放。这些会影响路由、权限、容量和成本。此文是方案，不代表已实现或已经接入生产。
